Compromised DMZ Web Server

A controlled incident-response exercise involving a Linux DMZ host with unauthorized accounts, privilege abuse, disabled host protections, and persistent malicious tooling. The objective was to identify the compromise, contain affected access, preserve evidence, reconstruct attacker activity, and document the incident using repeatable DFIR procedures.

Incident ID INC-2026-0907-001
Affected Host WEB-DMZ-01
Evidence Host EVIDENCE01
Environment Controlled training lab

Executive Summary

Investigation of WEB-DMZ-01 identified signs of unauthorized administrative access, including suspicious local accounts, elevated privileges, a stopped host firewall, hidden files, a malicious persistence mechanism, and a suspicious service/process chain.

Containment actions included disabling unauthorized accounts, removing interactive shell access, restoring host firewall protections, reviewing active network listeners, and isolating suspicious persistence components for preservation and analysis.

Portfolio context: This was a simulated incident in a self-contained lab environment. It is presented as hands-on DFIR training and not as a production breach.

Initial Findings

  • webadmin observed as an active account.
  • sysmaint identified as a newly created account with wheel privileges.
  • Host firewall found stopped during the investigation.
  • Suspicious hidden file discovered on the host.
  • Suspicious artifacts identified at /tmp/.system-update and /usr/bin/system-update.
  • Persistence associated with system-update.service.
  • Suspicious process activity associated with PID 18579.

Tools & Techniques

Linux journalctl systemd ss SHA-256 SFTP Chain of Custody Evidence Preservation Process Analysis Network Review

Containment Actions

  • Locked the webadmin and sysmaint accounts.
  • Disabled interactive shells for unauthorized accounts to prevent further login activity.
  • Restarted firewalld to restore host-level filtering.
  • Attempted a deny-all containment posture while preserving investigative access.
  • Reviewed active listeners and network services with ss -tulpn.
  • Stopped and isolated the suspicious system-update persistence mechanism for evidence handling.

Evidence Preservation

Evidence was copied using preservation-aware methods, hashed with SHA-256, documented in a chain-of-custody manifest, and transferred by SFTP to a dedicated evidence host. Pre- and post-transfer hashes were compared to verify integrity.

Evidence Type Examples Preserved
Suspicious executables/scripts .system-update, system-update, related scripts
Persistence system-update.service
Network/process state Process listings, listening ports, network snapshots
SSH artifacts Private/public keys, known_hosts
Supporting files net-check, .hosts, PID-related artifacts
Documentation Chain-of-custody record, manifest, SHA-256 verification log

Log & Artifact Review

The investigation used system and authentication logging to correlate account use, persistence execution, and supporting processes. Review included:

  • journalctl searches for SSH and account activity.
  • Service logs associated with system-update.
  • Logs related to net-check and associated system activity.
  • Process and network-state snapshots to identify suspicious runtime behavior.
  • Filesystem review to identify hidden and unusual artifacts.

Chain of Custody

A chain-of-custody record was created for the incident using the incident ID, evidence ID, source host, collector identity, collection timestamps, transfer method, and integrity-verification results.

  • Source: WEB-DMZ-01
  • Destination: EVIDENCE01
  • Transfer: SFTP
  • Integrity method: SHA-256
  • Evidence identifiers: E001–E011

MITRE ATT&CK Mapping

A formal ATT&CK mapping was not recorded during the original exercise. Based on the observed behaviors, likely areas for future mapping include account creation, privilege escalation, persistence through system services, credential/SSH artifact use, and defense impairment.

I would keep the portfolio wording exactly this cautious unless you later document specific technique IDs from your lab notes. It is better to show disciplined analysis than to force an unsupported ATT&CK mapping.

What I Learned

  • Containment decisions must balance stopping attacker activity with preserving enough access to collect evidence.
  • Hash verification before and after transfer is critical for demonstrating evidence integrity.
  • Persistence can be distributed across accounts, scripts, binaries, services, and startup mechanisms.
  • Host logs become more useful when correlated with process state, filesystem artifacts, and network listeners.
  • Chain-of-custody documentation should begin during collection, not after the technical work is finished.
